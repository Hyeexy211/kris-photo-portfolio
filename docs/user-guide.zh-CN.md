# Kris Photography 使用说明

> 本说明对应仓库当前源码。2026-09-23 已在 Supabase 完成内容字段及外键迁移，并通过当前源码的 HTTP 预览连接真实云端，完成所有者增删改查、图片上传／替换和作品集编排复测。测试后原有 3 个作品集、9 张照片逐字段（含时间戳）与基线一致，15 个测试网页图已清理。匿名新增记录和上传被拒绝；第二个已登录非管理员账号及其他负向权限用例仍待验证。源码发布状态需另行核对。

## 1. 这是什么网站

这是一个用 HTML、CSS 和原生 JavaScript 制作的摄影作品集。访客可以浏览作品集和照片；站点所有者可以进入有登录门槛的云端编辑界面，也可显式打开浏览器本地原型。当前仓库的默认内容是 **3 个作品集、9 张照片**，分别属于 Portrait、Documentary、Landscape。

公开站点首页、Gallery 和通用作品集页优先从 Supabase **只读**获取内容。如果任一组云端内容读取失败，页面会把作品集和照片一起切换到当前浏览器里的本地数据。这个回退只是保证页面还能显示，不代表本地编辑会自动上传到云端。

## 2. 访客怎样使用

公开地址：<https://hyeexy211.github.io/kris-photo-portfolio/>。此前合并版本的首页与主要静态资源已在线核对；本次源码发布后仍需检查公开站点。真实云端上传已通过当前源码的 HTTP 预览验证，这不代表 GitHub Pages 已自动更新。

| 目的 | 操作 | 当前结果 |
| --- | --- | --- |
| 看作品集 | 在首页点 **Collections** 中的 Portrait、Documentary 或 Landscape 卡片 | 进入 `collection.html?slug=...`，浏览该作品集的照片；三个旧版 `projects/*.html` 页面也保留。 |
| 看全部照片 | 点首页导航的 **Gallery** | 默认显示全部照片。 |
| 按类型筛选 | 在 Gallery 点 **All / 全部** 或当前照片实际使用的分类 | 分类按钮从 Photo 的 `category` 去重生成；没有照片的 Street 不显示。内置分类随界面语言翻译，新分类保留填写的原文。 |
| 放大照片并查看资料 | 点 Gallery 或作品集中的照片，再点灯箱内 **Photo details / 照片信息** | 灯箱可用左右按钮或键盘 ← / → 切换，按 Esc 退出；手机可在大图上左右滑动，信息区可独立滚动。只显示已填写的拍摄资料；全部为空时提示“暂无拍摄信息”。 |
| 看单张照片 | 在灯箱标题旁点 **View photo** | 现有 9 张照片进入各自的 `photos/照片ID.html` 页面。新增云端照片目前使用通用 `photo.html?id=照片ID`。 |
| 下载网页尺寸图 | 在现有照片的单张页面点 **Download web-size photo** | 下载仓库内对应的 1200px WebP 网页图；它不是 1800px 展示图或原片。新增云端照片暂不提供此按钮。 |
| 手机浏览 | 点页头菜单按钮 | 展开导航；选链接或按 Esc 可关闭。 |

有日期的照片会在首页 Gallery 中按日期从新到旧排列；没有有效日期的排在后面，并保持原有相对顺序。作品集内可另排照片顺序，不改变 Gallery 的顺序。当前 9 张默认照片的拍摄日期均为空，因此不会凭文件时间推断拍摄日期。拍摄日期与时刻分开保存；地点和器材等资料只有在已确认、已填写时才出现在灯箱和单张照片页。

## 3. 网站所有者怎样试用本地内容编辑

1. 显式打开 `admin.html?mode=local`，或在后台页面中点 **Browser-local editor**。此模式无需登录；无参数的 `admin.html` 默认是 Cloud Admin，旧地址 `admin.html?mode=cloud` 仍可使用。
2. 在 **Manage Works** 中新增作品集，或点已有条目的 **Edit**。保留稳定 ID 与 slug；填写标题、短介绍、可换行的创作故事、真实封面路径、封面替代文字和显示顺序，点 **Save Work**。本地模式的封面路径必须指向项目内已有图片。
3. 在作品集下方的选照区选择作品集，可按标题或分类查找。勾选真实缩略图后点 **Add selected / 加入所选照片** 或 **Remove selected / 移出所选照片**。加入其他作品集中的照片会先提示“移动归属”，照片仍只有一个 `collectionId`。用上移／下移按钮调整集内顺序，再点保存排序。若批量操作中途失败，状态会说明已保存数量并重新读取实际列表。
4. 在 **Manage Gallery** 中新增或编辑照片：填写真实图片路径、分类、可选作品集、全局顺序、集内顺序及已确认的日期、拍摄时刻、地点和器材。分类可选已有名称，也可输入新名称；标签用英文逗号分隔。点 **Save Gallery Item** 保存。下方的分类重命名／合并会把旧分类中的照片逐条改派到目标分类，不会删除照片。
5. 本地模式可以选一张文件仅用于 **JPEG EXIF 候选值审核**，该文件不会上传或变成项目图片。逐字段查看、修改、接受或拒绝；“接受”只把候选值复制到照片表单，仍须点保存。手工已填字段不会因重新选图自动覆盖。无 EXIF、损坏 EXIF 或不支持的格式会提示“未读取，可手填”；地点仍须手工确认，GPS 坐标不会进入表单或公开资料。
6. 删除作品集前会显示关联照片数及结果；确认后照片解除关联，仍留在 Gallery。单独删除照片仍是另一项明确操作。页面底部的 **Reset Content** 会在确认后把当前浏览器里的 Works 和 Gallery **全部恢复为仓库默认种子**，覆盖本地修改。

本地模式只把记录保存在当前浏览器的 `localStorage`。它不会修改 `data/` 文件、图片文件、Supabase、Git 仓库或其他设备。图片字段在本地模式填写的是**已有图片的相对路径**；表单不会把选中的图片文件上传进项目。路径必须真实存在且大小写一致，否则浏览器会显示坏图。

**当前容易误解的一点：**公开页面的配置优先读 Supabase。云端读取正常时，`admin.html?mode=local` 的本地修改不会出现在公开首页和作品集页；只有页面使用本地数据源或触发本地回退时才可能看到这些记录。因此，不要把这个本地原型当作正式发布工具，也不要用它判断云端内容是否已经更新。`file://`、`http://127.0.0.1:4173` 与 GitHub Pages 也是不同的浏览器来源，三处的本地存储不会自动互通。

## 4. 本地预览与项目文件

在项目根目录运行：

```sh
python3 -m http.server 4173 --bind 127.0.0.1
```

然后在浏览器打开 `http://127.0.0.1:4173/` 看当前源码，或打开 `http://127.0.0.1:4173/admin.html` 看默认 Cloud Admin；试用本地原型请打开 `http://127.0.0.1:4173/admin.html?mode=local`。运行服务器的终端中按 `Ctrl+C` 停止。直接双击 `admin.html` 得到的 `file://` 地址不是线上网站；页面会提示改用线上或 HTTP 预览地址，不能用它判断云端发布结果。已有的 `file://` 本地记录仍属于原浏览器来源，不会自动转到 HTTP 或 Supabase。

| 位置 | 用途 |
| --- | --- |
| `index.html`、`collection.html`、`photo.html`、`photos/`、`projects/` | 首页、通用作品集页、通用照片页、9 张现有照片的独立页和保留的旧作品页。 |
| `data/collections.js`、`data/photos.js` | 浏览器本地默认内容；不要填写未经确认的拍摄资料。 |
| `js/content-service.js`、`js/repositories/` | 公开页面的数据读取和本地数据保存。 |
| `admin.html`、`js/admin.js` | 默认 Cloud Admin；`?mode=local` 保留本地编辑原型。 |
| `images/`、`css/` | 真实照片、响应式网页图和页面样式。 |
| `dist/` | Sites 预览和托管所用的静态副本，已被 Git 忽略；它不等于根目录源码。 |

如果要预览 `dist/`，可改用 `python3 -m http.server 4173 --bind 127.0.0.1 --directory dist`。修改根目录源码后，要先同步对应文件到 `dist/`，否则看到的可能是旧内容。不要只修改 `dist/`。

## 5. 云端数据与 Cloud Admin 的现状

- **已核对的云端读取和身份：**公开页面通过 Content Service 一起读取 Collections 和 Photos；云端读取异常时会一起回退到浏览器本地内容。真实所有者已登录，管理员检查返回通过；前一轮临时记录新增、删除和分类批量修改也已成功。不能把本地回退误认成云端写入成功。
- **2026-09-23 已修复的数据库配置：**`story`、`collection_order`、`capture_time` 已完成迁移，作品集外键已改为 `ON DELETE SET NULL`。迁移前后原记录数量、旧字段和时间戳一致。控制台还确认 `portfolio-web` 公共网页图桶、`portfolio-originals` 私有原图桶及 4 条所有者 Storage 策略均已存在，核查时两个桶均为空；没有重跑 Storage 迁移。此前浏览器的 `getBucket()` 错误不能证明桶不存在，因为桶元数据读取与对象上传使用不同权限。
- **迁移后已通过真实云端复测：**新增 1 个临时作品集和 2 张临时照片，编辑故事，保存／清空拍摄时刻，替换封面和照片，批量加入／排序／移出，分类重命名及公开筛选，删除含照片的作品集并保留照片，最后删除临时照片。集内顺序不改变 Gallery 全局顺序。测试后原记录逐字段与基线一致；15 个测试网页图（含替换前版本）已删除，测试路径列表为空，最终 SQL 核查 Storage 对象数为 0。
- **权限验证范围：**匿名数据库新增返回 `42501`，匿名 Storage 上传返回 `403`。第二个已登录非管理员账号、重复键覆盖和其他 Storage 拒绝场景尚未完成实测。详细结果与边界记录在 [`crud-test-report-2026-09-23.md`](crud-test-report-2026-09-23.md)。
- **图片上传的设计边界：**Cloud Admin 接受最长边至少 1800px、文件不超过 25 MiB、总像素不超过 4000 万的 JPEG、PNG、WebP 或可解码 AVIF，横图和竖图均可。选择后可看预览；不选新文件就保留原图。选择文件时先在浏览器本地尝试读取 JPEG 的常见 EXIF 候选值，只有逐字段接受并保存后才公开。保存时浏览器经 Canvas 保持比例，按最长边生成 640、1200、1800px 三份 WebP，`srcset` 使用各导出图的实际宽度；检查无 EXIF/XMP 后上传，再把 URL 写入 Supabase。原始文件不会上传，替换后的旧网页图暂不自动删除。浏览器本地原型仍使用已有图片的相对路径字段。详情见 [`supabase-admin-setup.md`](supabase-admin-setup.md) 与 [`supabase-storage-setup.md`](supabase-storage-setup.md)。

Cloud Admin 的使用步骤如下；后续权限验收应继续使用可删除的临时记录：

1. 在站点根地址后加 `admin/` 打开 Dashboard，登录所有者账号，进入 **Manage Work** 或 **Manage Gallery**。公开页面不显示 Dashboard 入口；也可在站点根地址后直接打开默认云端模式的 `admin.html`。旧地址 `admin.html?mode=cloud` 仍兼容。
2. 新建 Collection 时填写标题等内容，点 **Choose image** 从电脑选封面，确认预览后保存。编辑时选择新文件可替换封面；不选择则保留当前封面。
3. 在 Gallery 新建或编辑照片时同样选择本地图片并确认预览，然后保存。上传过程中保存按钮不可重复点击；失败时先看表单状态和错误信息，不要把未确认的 URL 当作已发布内容。

Cloud Admin 写入 Supabase 后，不能直接改写 GitHub Pages 上的静态 HTML。现有 9 张照片的独立分享页及其社交预览资料需要重新生成、审核并发布；新云端照片暂时只有通用照片页。公开仓库中仍保留原片，因此网页尺寸下载限制**不等于**原片已受到保护。

## 6. 新字段迁移和发布

1. 当前生产库已于 2026-09-23 执行 [`20260923_collection_content.sql`](../supabase/migrations/20260923_collection_content.sql)，补齐作品集内顺序并将作品集删除改为解除照片关联。迁移后已查实 `collections.story`、`photos.collection_order`、`photos.capture_time` 及 `ON DELETE SET NULL` 外键。现有项目无需为同一缺字段问题重复执行；新环境仍应先核对实际表结构、触发器和策略再补齐缺口。
2. 所有者身份、管理员配置、Storage 桶及策略已查实，所有者增删改查及上传链路已复测通过。继续按 [`supabase-admin-setup.md`](supabase-admin-setup.md) 和 [`supabase-storage-setup.md`](supabase-storage-setup.md) 补齐第二个已登录非管理员账号及剩余负向权限用例；每次仍使用临时记录，结束时清理本轮记录和网页图，核对原有内容与测试前快照一致。
3. 从根目录源码同步本次改变的页面、脚本、样式、语言包与图片到忽略的 `dist/` 托管预览副本，核对内容一致后再按项目流程提交、推送、发布，并复查桌面、手机、资源请求和控制台。Cloud Admin 修改现有 9 张照片后，运行 `node scripts/generate-photo-pages.js --source=supabase`，审核 `photos/` 生成差异；新增或删除照片还需人工检查 `sitemap.xml`。这些静态文件不会随后台保存自动更新。
